Kite Wallah

This page documents the full decision logic in the app. It should be updated whenever recommendation behaviour changes (see AGENTS.md in the repo).

How it works

Kite Wallah combines forecast data (Open-Meteo wind, optional tides), your spots (safe wind sectors, tide launch windows), rider profiles (weight, sex, ability), a shared crew quiver, and logged sessions to answer: should we go, when, and which kite?

End-to-end pipeline (single source of truth)

Every Plan day and Now recommendation follows the same ordered pipeline. There is no separate “chat guess” path for kites — optional AI only explains what the code already computed. Implementation modules are listed so you can trace behaviour in the repo. 

Forecast (Open-Meteo)
  → hourly assessments (planner.js, assessSuitability in engine.js)
  → best powered window (planner.js)
  → day verdict per rider (planner.js)
  → recommendKite() for solo pick (engine.js + calibration.js + kite-personal-range.js)
  → [crew day] allocateKitesFairly() (fair-kite-allocation.js)
  → rider card copy (buildRiderKiteDisplayHtml)
  → “From your log” note (session-comparison.js)
  → bring-kit union (plan-bring-kit.js)

Three inputs are deliberately balanced (not “chart wins” or “sessions win” alone):

  • Thesis — chart & physics: manufacturer wind range, weight/sex adjustment, generic ideal size formula, gust character.
  • Antithesis — your sessions: per-kite comfort ranges, preferred size near this wind, underpowered/overpowered feelings.
  • Synthesis — physical constraints: one kite per person in the bag; heaviest assigned first; rent only when the bag truly cannot work.

1. Inputs the app uses

  • Rider profile — name, weight, sex (required — male or female) for manufacturer wind-range adjustment, ability level, optional skills metadata. Plan and Now won’t run until every selected rider has sex set.
  • Shared quiver — all kites/boards in the Quiver tab; every rider’s recommendations can use the full list (not a fixed “4 kites per rider” assignment).
  • Sessions — after you log a session, entries tune comfort ranges per kite (and lightly per size class across brands).
  • Spot — lat/lon, water type, safe wind sectors (offshore = no-go), optional tide rule (launch only within N hours of high/low).
  • Forecast — hourly wind speed, gusts, direction; daylight from sun times; tides when available.

2. Ability → wind bands

Your ability dropdown sets a personal wind band: minimum wind you can ride in, maximum before it feels too strong, and how much gust spread you tolerate. Examples:

  • Competent — about 12–26 kt, gust spread up to ~9 kt.
  • Intermediate — about 14–24 kt, tighter gust tolerance.
  • Expert — wider band and higher gust tolerance.

Plan uses these limits for every hour and for the day verdict. The Now tab uses the same bands but with slightly different verdict thresholds (more forgiving for “right now”).

3. Plan: each forecast hour (decision tree)

For every hour in the forecast, the app builds an hour assessment:

  1. Wind suitability — score vs ability band (Plan is stricter than Now: bottom of your range is marginal, not “ideal”).
    • Very gusty (large gust minus average) → score capped, notes say gusty — never called “light wind”.
    • 12–13 kt for a competent rider → often marginal even if “rideable”.
    • Verdict per hour: good, marginal, or bad.
  2. Spot launch — is wind direction inside your safe sectors? Offshore → not rideable.
  3. Tide rule (if set) — is this hour inside your launch window around high/low tide? Outside → tide-blocked (dimmed on timeline).
  4. Daylight — after sunset (unless “Include night hours”) → dark, not scorable.
  5. Best kite for that hour — recommendKite on the active kite list (home quiver, packed bag, or full catalog if renting). Shown as size on the timeline after the plan loads.

Timeline colours = wind strength. Cross-hatch / dim = outside tide window. Arrow = direction wind blows (toward sea).

4. Plan: best powered window

The hero line “Ride 16:00–19:00” is not “any time you’re free” — it’s the best powered block:

  1. Only hours that are rideable (launch OK, tide OK, not dark).
  2. Only hours at least minWind + 2 kt for your ability (actually powered, not fringe).
  3. Group contiguous powered hours into runs of 2+ hours.
  4. Score each run: favour steady wind (small dips and low variance), many “good” hours, penalise big gust spread and deep lulls inside the run.
  5. Pick the highest-scoring run → that becomes avgWind, peakGust, windowLabel.

Separate logic refines timing tips (e.g. “15:00 is a brief spike; 16:00+ is steadier”) by comparing hourly wind inside and outside that window — so advice can be narrower than the wide window shown in the hero.

5. Plan: day verdict (GO / Possible / Maybe / …)

From scorable hours and the powered window:

  1. Skip — no rideable hours, or nothing powered enough.
  2. Probably not — mostly marginal / weak powered time.
  3. Maybe — some powered time but thin or very gusty window.
  4. Possible — workable but not a clean window (gusty or few good hours).
  5. GO — solid powered window (typically 2+ good powered hours, average wind in the sweet band). Very gusty windows may downgrade GO → Possible.

Multi-rider days show one shared hero (date, spot, crew ride window) — per-rider GO/Maybe and kite lines are only on the rider cards below.

6. Choosing a kite (core scoring tree)

Every kite pick (Plan day, Plan hour, Now, allocation) uses the same core engine:

  1. Manufacturer chart — brand/model/size from the catalog, adjusted for rider weight and sex.
  2. Model character — same size, different models (e.g. Orbit vs Evo) get different effective ranges (freeride vs C-shape, etc.) via kite-character.js.
  3. Session-tuned range — for each kite:
    • 100% weight: sessions logged on this kite id.
    • ~35% weight: same-size sessions on other quiver kites (cross-brand hint).
    • Builds fun min / comfort max / push max from feelings (too small, just right, overpowered, couldn’t ride).
  4. Score at this wind — how well current wind sits in the effective range; calibration nudges toward your historical preferred size at similar wind; small boost if high-confidence session data on this kite; character adjust for gusty vs steady days.
  5. Pick highest score — top kite + alternates; human-readable reason line (in/out of range, session-backed, etc.).

Important: Recommendations use the shared quiver for all riders. Session count on a rider shows how many logs they have — not “number of kites owned.”

7. Plan: day kite line & advice

Using the powered window averages (not a single random hour):

  1. Run recommendKite on the rider’s kite list for window avg wind + peak gust.
  2. If session calibration is high confidence with a preferred size, may swap to a closer size in the quiver when it scores nearly as well.
  3. Build kite line — steady wind vs gusty advice (may suggest smaller kite when gust spread is large).
  4. Skip note — e.g. “Skip before 16:00 — only 12 kt and underpowered” if early hours are weak (shown once under “What to expect”, not repeated per rider).
  5. What to expect on the water — launch, gust handling, crew-level summary; includes “Best time on the water” timing tip when relevant.

8. Plan: hourly sizes on the timeline

After the day plan is built, each scorable hour gets a size label (e.g. 10m, 11m):

  • Run recommendKite at that hour’s exact wind and gust.
  • Green / amber / none = fit quality (in range + score thresholds).
  • Tooltip shows kite name, fit %, gusts, optional alternate.

9. Multi-rider: who flies what (fair allocation)

When two or more riders plan the same day at the same spot (and travelling mode is not “renting”), allocateKitesFairly() in fair-kite-allocation.js runs once per day using the crew ride window wind: average speed and peak gust from the shared hero (same values as each rider’s solo Plan line).

  1. One shared forecast timeline and hero (crew window) — planner-ui.js.
  2. For each rider whose day verdict is not Skip, build conditions: weight, sex, ability, spot notes, windSpeed = avgWind, gustSpeed = peakGust, water type — profileToConditions().
  3. Kite list = shared quiver at home, or ticked “packed bag” ids when travelling with kites. Renting mode skips allocation entirely (each rider gets an independent catalog pick).
  4. Step A — score matrix: for each rider, score every kite in the bag (see §10). Also compute solo pick = recommendKite(conditions, allKites, calibration) (what they would ride if alone).
  5. Step B — assign kites (one physical kite each):
    • Sort riders by weight descending (heaviest first).
    • Heaviest: pick unused kite closest to power target (not “largest in bag”).
    • Next riders: if solo kite still free and scores ≥ 45%, keep solo; else pick among remaining kites — prefer scores ≥ 45%, else session-adequate size, else best need-fit; then closest to power target.
    • Each kite id used at most once.
  6. Step C — accept or decline assignment:
    • Score ≥ 45% → normal assignment.
    • Score < 45% but kite still in bag and not declined by session/wind rules → assign as Use from bag (compromise).
    • Only mark unassigned + Last resort: rent when no kite left, or the only leftover fails minimum session size / is dangerously underpowered on chart (see §10).
  7. How to split kit when it is tight — plain-language conflict note when anyone is unassigned; lists who got what from the bag and reminds you to use leftovers before renting.
  8. Rider cards: verdict + kite lines from buildRiderKiteDisplayHtml(); optional “From your log” line; wind story stays in hero / What to expect only.

10. Need score, power target & thresholds

Crew allocation does not reuse the solo 0–100 score blindly. It builds a need-fit % per rider × kite, then applies assignment rules. Constants (current code):

  • 45 — MIN_SUITABLE_SCORE: “good enough” for a normal assignment.
  • 15 — MIN_HEAVY_TARGET_SCORE: heaviest may keep a session-driven target kite with a low chart score.
  • 12 — MIN_BAG_LAST_RESORT_SCORE: below this, a leftover kite is never forced from the bag.

10.1 Solo score (starting point)

For each kite, need starts from recommendKite(conditions, [thatKite], calibration).score — the same engine as Plan/Now (catalog range, session-tuned effective range, calibration boost/penalty, gust character). See §6.

10.2 Chart size vs ideal (when sessions don’t justify the size)

Compute ideal size (m²) for this wind and weight: (42 − windKt) / 2.8 × (weight / 75)^0.4, rounded to nearest 0.5 m (idealKiteSizeForWind in engine.js). Compare kite size to ideal:

  • More than 1 m larger → large penalty (chart says overpowered).
  • 0.5–1 m larger → medium penalty.
  • More than 1 m smaller → penalty (underpowered vs chart).
  • 0.5–1 m smaller → small penalty.

Session override: if the kite lies in the band [session power floor − 0.5 m … session power floor + 2.5 m], those oversize penalties are not applied, and a +18 boost is applied when size ≥ floor − 0.25 m. Floor = max(minimum adequate size, typical preferred size near this wind). This is why an 11 m can score well for a rider who was underpowered on 9 m in a similar-wind log even when the chart ideal is ~9 m.

10.3 Minimum adequate size from sessions

inferMinAdequateKiteSize(wind, calibration, weight):

  1. Consider sessions with wind within ±4 kt of today’s window average.
  2. For each entry with an underpowered feeling, compute preferred size = logged kite size + feeling adjustment (e.g. slightly underpowered on 9 m → 9.5 m; underpowered-rideable on 9 m → 10 m). See feeling table in §14.
  3. If today’s wind is lighter than that session (by more than 2 kt), add up to +1.5 m extra need (0.5 m per 4 kt lighter, capped).
  4. Take the maximum across matching sessions; add +0.5 m for riders ≥ 88 kg, another +0.5 m for ≥ 98 kg.
  5. In need score: kite more than 0.25 m below minimum → −40; at or above minimum → +28.

10.4 Typical size near this wind

getCalibrationAtWind(wind, entries) weights all sessions (stronger weight within ±6 kt), maps each to a preferred size via the same feeling adjustments, and returns a weighted preferredSize plus confidence (none / low / medium / high). This feeds both the session power floor and the power target.

10.5 Power target (who should hold how much power)

targetPowerSizeForRider = maximum of:

  • chart ideal size for weight at window average wind;
  • minimum adequate size (if any);
  • preferred size from calibration (if any);
  • solo pick size — only if solo score ≥ 40 and size ≥ target − 0.25 m.

Heaviest rider: among unused kites, choose the one closest to this target (prefer smallest kite still ≥ target − 0.5 m). Lighter riders: after normal suitability rules, also prefer closest to target among remaining kites. This is not “heaviest always takes the biggest kite in the bag.”

10.6 When rent is shown

Rent is last resort copy only. A rider is unassigned (and rent suggested) when:

  • no unused kite remains; or
  • the only leftover kite scores < 12% need-fit; or
  • leftover is more than 0.5 m below session minimum adequate size; or
  • wind is more than 1.5 kt below catalog minimum for that kite; or
  • leftover is more than 1.5 m smaller than chart ideal and chart band is “light” / underpowered.

Otherwise they are assigned with Use from bag and an amber warning even if need-fit is 40–44%. Suggested rent size uses the same power target logic (may bump up if the only leftover was too small).

11. “From your log” comparison (Plan rider cards)

Separate from allocation scoring but uses the same session data. buildRelevantSessionNote() in session-comparison.js picks one past session to explain the day card:

  1. Pick session: prefer same spot id/name; else any log. Sort by wind match (± wind speed and gusts). Drop if best match is more than 8 kt off forecast average.
  2. Relevance gate — show note only if at least one of: wind within 3 kt; same spot and within 6 kt; under/overpowered feeling within 6 kt; recommended size differs by ≥ 1 m from logged kite within 6 kt; gust spread change ≥ 4 kt; spot notes within 5 kt.
  3. Lead line may prefix: “You were underpowered in similar wind before —” when feeling was underpowered; or size vs today’s assigned kite differs.
  4. Body — date, spot, wind then vs forecast now, kite name, feeling text, optional gust/water/notes. Allocation already uses underpowered entries for minimum adequate size; this line is explanatory, not a second hidden rule.

Crew “From your logs” in What to expect uses buildCrewPastSessionLines() — one similar log per rider (deduped), not the same algorithm as allocation.

12. Travelling mode (Plan setup)

Tap Travelling: off on Plan to turn trip mode on (default is off — full crew quiver at home). When on, choose:

  • We brought kites — tick only the kites in the bag. All scoring, hourly picks, allocation, and bring-kit use only those ids.
  • Renting (nothing packed) — kite list = full catalog (all brands/sizes, weight-adjusted). Hourly and day picks are best rental matches; multi-rider does not fight over one physical kite — each rider gets their own catalog pick.

13. What to bring / rent (end of day card)

Risk-averse crew bag summary after all recommendations:

  1. Walk hours in the main powered ride window only; collect kites that cover those hours.
  2. Add adjacent sizes in your quiver (one up / one down) when a size is needed in that window.
  3. Merge across riders → union of kites (multi-rider).
  4. Rental suggestions only when the quiver has no viable kite for that window — not for gust insurance or weak pre-window hours.

Shown at the bottom of the day card as a consolidated recap.

14. Now tab

  1. Current (or manual) wind at selected spot.
  2. Same spot rules (sectors, tides) and ability band.
  3. assessSuitability + recommendKite per selected rider.
  4. Verdict: GO / Possible / … (slightly different thresholds than Plan).
  5. Multi-rider Now: same fair allocation when several riders selected and spot is rideable.

15. Sessions & calibration

  • Logging records wind, gusts, direction, kite used, spot, board, water state, and a how it felt slider (nine steps from very underpowered to very overpowered).
  • Each feeling maps to a size adjustment when inferring “what size would have been right”:
  • Couldn’t ride / very underpowered → +1.5 to +2 m vs kite used
  • Underpowered (rideable) / too small → +1 m
  • Slightly underpowered → +0.5 m
  • Just right / comfortable → no change
  • Slightly overpowered → −0.5 m
  • Overpowered (rideable) → −0.75 m
  • Too big → −1 m
  • Very overpowered → −1.5 m
  • Per-kite range tuning (kite-personal-range.js): sessions on this kite id (full weight); same-size sessions on other quiver kites (~35% weight). Builds effective min / comfort max / push max from feelings.
  • Score nudge (applyCalibrationToScore): near forecast wind, boost kites close to preferred size; penalize far off (stronger when confidence is high).
  • Does not remove kites from the quiver — it changes scores, ranges, allocation minimums, and Plan notes.

16. Live shared data

When Supabase is configured, crew quiver, riders, spots, and sessions sync for everyone. A green pulsing dot and Live shared data means cloud sync is active. If load fails, the app still opens using this device’s cache; use Retry in the banner.

17. AI chat (optional)

Built-in rules answer basic questions without payment. Optional OpenAI key under Plan → Options powers richer Plan/Now chat; key stays in your browser only.
